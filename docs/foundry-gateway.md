# New Foundry invocation gateway (ASC-24)

`sous_chef.adapters.foundry_gateway.FoundryGateway` is the backend boundary for
invoking the two managed interactive agents. It uses the pinned
`azure-ai-projects==2.8.0`, `openai==3.27.0` and `azure-identity==1.26.0`
baseline, New Foundry project API **v1**, and project-integrated
**Responses v1** (`/openai/v1/responses`). `aiohttp==3.14.4` supplies the
async Azure credential/project transport. This is not the classic Agents SDK,
Assistants/Threads/Runs, or direct-model Chat Completions.

Each request supplies an `agent_reference` with an approved runtime **name and
version**, never a `model` override. There is no provider, credential, model-only,
or local-success fallback. The existing ASC-10 `FoundryModelClient` and
`check_foundry` command remain model-deployment wiring diagnostics; they are not
used by this gateway and must not replace managed-agent invocation.

## Configuration

Use the existing `.env.<environment>` selection and required live app settings.
Gateway construction requires `ASC_ADAPTER_MODE=live` and these values:

| Setting | Requirement |
| --- | --- |
| `ASC_FOUNDRY_PROJECT_ENDPOINT` | Intended New Foundry project HTTPS endpoint |
| `ASC_FOUNDRY_ORCHESTRATOR_AGENT_NAME` | Deployed Orchestrator runtime agent name |
| `ASC_FOUNDRY_ORCHESTRATOR_AGENT_VERSION` | Explicit positive numeric version, not `latest` |
| `ASC_FOUNDRY_RECIPE_NUTRITION_AGENT_NAME` | Different deployed Recipe + Nutrition runtime name |
| `ASC_FOUNDRY_RECIPE_NUTRITION_AGENT_VERSION` | Explicit positive numeric version |
| `ASC_FOUNDRY_INVOCATION_TIMEOUT_SECONDS` | Positive finite total deadline, at most 120 seconds; default 60 |
| `AZURE_CLIENT_ID` | Required in dev/prod: App Service user-assigned managed identity client ID |

Names and versions are optional for the application scaffold, but mandatory when
constructing this gateway. Versions are configuration pins, not discovered or
silently upgraded at invocation time.

In dev/prod, the credential factory constructs only `ManagedIdentityCredential`;
missing identity configuration fails rather than trying developer credentials,
environment secrets, or API keys. Explicit local live development uses only
`AzureCliCredential` (`az login`). It does not impersonate the deployed workload.

Keep the App Service client/principal ID, runtime agent name/version, and each
agent's Entra identity separate. ASC-11 supplies workload access; ASC-12 binds
distinct Entra Agent identities and tools. The gateway invokes those configured
agents; it does not rebind identities, provision tools, or accept an agent name
from an HTTP request.

## Backend use and contract

```python
from sous_chef.adapters.foundry_gateway import FoundryGateway
from sous_chef.domain.agent_identity import AgentRole
from sous_chef.domain.foundry import FoundryRequest

gateway = FoundryGateway(settings)
result = await gateway.invoke(
    FoundryRequest(
        role=AgentRole.ORCHESTRATOR,
        prompt=authorized_backend_context,
    )
)
```

The frozen, strict `FoundryRequest` bounds the nonblank prompt to 16,000
characters and output-token budget to 16-8,192 (default 2,048). Its opaque UUID
`operation_id` is generated by default; trusted backend code may supply its own
UUID to correlate a larger operation. It travels as `X-Client-Request-Id` and
is returned on both `FoundryResult` and `FoundryGatewayError`. Operational logs
use the same UUID's hex form as `trace_id`; the caller's logging context is
restored afterward. Correlation is **not** an idempotency guarantee.

`FoundryResult` contains the role, operation UUID, service response ID and
nonblank text (at most 131,072 characters). Only a schema-valid, completed
response without an error, incomplete details, or refusal is accepted.
Empty, partial, queued, failed and malformed responses cannot become success.
Prompt and result text are excluded from object representations.

The gateway has no conversation/previous-response ID input and never accepts
user credentials. The caller must authenticate and authorize the user, assemble
bounded context with explicit-over-learned precedence, and persist history
under that user's ownership. Output is not an approved recipe: final structured
recipe validation and deterministic allergy checks remain mandatory before
display or persistence. This issue adds no chat route or agent instructions.

## Failure and cancellation contract

`FoundryGatewayError` exposes a safe `code`, `role` and `operation_id`.
Do not serialize the raw SDK exception, service body or traceback to a user.

| Code | Meaning |
| --- | --- |
| `foundry_authentication` | Token acquisition failed, or service returned 401/403 |
| `foundry_throttled` | Service returned 429 |
| `foundry_timeout` | Total deadline, SDK timeout, or upstream 408/504 |
| `foundry_invalid_result` | Invalid response schema, unfinished/refused/empty/oversized result |
| `foundry_unavailable` | Connection/transport failure or other upstream 5xx |
| `foundry_rejected` | Other service rejection, including incorrect agent/version configuration |

The total async deadline covers credential/client setup, the network operation
and response handling. Both Azure SDK and OpenAI automatic retries are disabled.
No invocation is automatically replayed, even for throttling or an ambiguous
connection failure. Any future retries require a proven safe/idempotent operation
and backend operation-state handling.

Cancel the awaiting task to cancel local in-flight work. `asyncio.CancelledError`
propagates unchanged, clients/credentials close, and no replacement run starts.
Cancellation or timeout does **not** prove that a remote agent stopped or never
started; do not blindly resend. Remote run lifecycle/reconciliation belongs to
the later chat integration.

Known failures log only an allowlisted category, operation correlation and
duration; cancellation and success have separate events. Programming errors are
not swallowed as service failures. Initialize `configure_safe_telemetry()` before
SDK use, as the app and smoke command do; never enable raw prompt/result tracing.

## Offline verification and approved dev smoke

Offline tests use the real OpenAI request/response layer with synthetic HTTP
transports and a test credential. No Azure account, network access or real
success impersonation is required:

```bash
python -m pytest tests/unit/test_foundry_gateway.py tests/unit/test_credentials.py
python -m ruff check .
python -m mypy
```

For the live acceptance check, first deploy the approved agents, pin their names
and versions, and supply the intended dev project and App Service identity
configuration. Run **inside the approved dev workload where that managed
identity is available**, not on a developer laptop after `az login`:

```bash
export ASC_ENVIRONMENT=dev
export ASC_APPROVE_FOUNDRY_SMOKE=1
python -m sous_chef.check_foundry_gateway
unset ASC_APPROVE_FOUNDRY_SMOKE
```

The explicit approval flag is process-only, not a saved default. This issues one
small request to each managed agent, can incur usage/tool costs, and is never a
startup or readiness probe. It refuses local/prod execution and exits nonzero on
failure. Output includes only role and operation ID, never the agent response,
project endpoint or credential. Successful invocation proves invocation wiring,
not recipe quality or final food safety. Record the successful operation IDs in
the reviewed dev acceptance evidence; offline tests are not a substitute for
that managed-identity smoke check.
